# 01 · 为什么选择 RAG · 掌握卡（入口版）

定位：S 级，开场必讲第一问；也是「项目介绍」的引子。
关联：02 Hybrid RAG、05 评测、08 系统可靠性（后续卡）。

## 1. 知识树

```
为什么选择 RAG
├── RAG 解决什么问题
│   ├── LLM 知识静态、过时
│   ├── 私有 / 新增知识不可见
│   └── 生成幻觉、答案不可溯源
├── 与替代方案对比
│   ├── 直接调用 LLM
│   ├── 微调 Fine-tuning
│   ├── 超长上下文硬塞
│   └── RAG（本项目选择）
├── RAG 的组成模块
│   ├── 知识库构建：Load → Chunk → Embed → Index
│   ├── 检索：QueryRewrite → HybridRetrieve → Rerank → Gate
│   ├── 生成：Prompt → LLM → Citation 校验
│   └── 支撑：缓存 / 会话 / 评测 / 观测
└── 关联知识
    ├── Embedding 与向量检索
    ├── 评测（Recall@3 基线）
    └── 高可用（熔断 / 降级 / 超时）
```

## 2. 核心流程（骨架）

场景 A：一次 RAG 问答

```
用户提问 → Query Rewrite → 混合检索 → Rerank → RelevanceGate
  ├─ 通过 → Prompt(带引用) → LLM → Citation 校验 → 返回带引用答案
  ├─ 不通过 → Prompt 告知「未找到」→ LLM 拒绝编造
  └─ LLM 超时 → 降级回复
```

场景 B：知识库更新

```
新增/修改文档 → SHA-256 变更检测 → 增量切分嵌入 → 索引重建 → 查询立即可见
```

## 3. 两分钟口述（骨架，第 3 步再展开）

- 结论先行：RAG = 检索 + 生成，解决「模型知识过时 + 私有知识不可见 + 答案不可溯源」。
- 原理：先检索相关资料，再让 LLM 基于资料生成。
- 为什么不用微调：更新成本、数据量门槛、可解释性、合规。
- 项目证据：15 篇文档 → 181 chunks、带 [N] 引用、门控拒答。
- 代价：检索质量决定答案上限；链路更长（评测 30 查询 ~14s）。
- 钩子：所以我把主要精力放在检索质量上 → 引出 Hybrid RAG。

## 4. 三个为什么（入口问题）

1. 为什么需要 RAG？ → 回答方向：静态知识 vs 动态私有知识、幻觉、溯源。
2. 为什么选 RAG 而不是微调？ → 方向：更新成本、数据量、可解释、合规；风格 vs 事实。
3. 为什么不用超长上下文直接塞？ → 方向：成本、窗口限制、长文本定位弱、无引用结构。

判定：三问都能用项目例子讲出「收益 vs 代价」→ 掌握；讲不出 → 标缺口，回知识树补结构。

## 5. 项目应用（证据映射）

| 场景 | 用了什么 | 收益 | 代价 / 坑 |
|---|---|---|---|
| 知识问答带引用 | CitationFormatter + CitationValidator | 答案可溯源、引用越界校验 | 目前 LLM 是 mock，最大差距 |
| 知识更新 | DocumentRegistry SHA-256 + 增量 ingestion | 改文档即生效 | rebuildBm25 无锁，低并发可接受 |
| 拒答防幻觉 | RelevanceGate（BGE 0.35） | 低相关不硬答 | 阈值需要评测集校准 |
